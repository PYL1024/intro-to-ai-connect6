# Intro to AI Connect6

## 0. 快速入口

- 课程答辩版文档：[README-defense.md](README-defense.md)

这是一个六子棋（Connect6）AI课程项目仓库。项目内包含多个学生组（`g06/g07/g08/g09/...`）的智能体实现、统一测试入口、以及若干搜索与评估模块。

本 README 重点介绍：

- 项目整体结构与运行方式
- 当前主要 AI 的决策流程
- 使用到的核心算法与背后原理
- 如何调参与扩展

## 1. 项目概览

### 1.1 Connect6 规则简述

- 棋盘为 $19 \times 19$。
- 一方先手首回合通常下一子，之后每回合下两子（代码中按 `Move(pos1, pos2)` 表示）。
- 率先形成至少六连的一方获胜。

Connect6 的分支因子显著高于五子棋：每回合是“二子组合决策”，候选点数量一多，搜索空间呈组合爆炸。因此项目实现采用了“启发式候选裁剪 + 威胁优先 + 博弈搜索”的混合架构。

### 1.2 主要目录

- `src/AITester.java`：统一测试入口（批量对局、联赛、单场对局）。
- `src/stud/g06`：V2 风格 AI（威胁防守 + Alpha-Beta）。
- `src/stud/g08`：V3 风格 AI（威胁空间搜索 TBS + Alpha-Beta + 更多工程优化）。
- `src/stud/g09`：V2/V3 混合强化版本（含 TBS、TT、候选扩展等）。
- `file.properties`：对局时限、GUI、默认玩家 ID 等配置。
- `lib/`：运行所需依赖（从仓库外拷贝时需确保完整）。

## 2. 如何运行

### 2.1 推荐方式（IDE）

1. 使用 IntelliJ IDEA 或 VS Code（Java 扩展）打开项目。
2. 确认 `lib/` 依赖已正确加入类路径。
3. 运行 `AITester.main()`。

### 2.2 测试入口说明

`AITester` 内置三类场景（通过注释切换）：

- `zeroCarnival()`：多 AI 随机循环赛（默认关闭 GUI，适合批量评测）。
- `oucLeague()`：主客场联赛（开启 GUI 可观察落子过程）。
- `oneMatch()`：自定义两名 AI 进行小规模对局。

### 2.3 常用配置（file.properties）

- `TimeLimit`：每个棋手总时间（秒）。
- `MaxStep`：最大步数上限，超出可判和。
- `GUI` 与 `Step_Inter`：是否显示图形界面与步间隔。
- `Player_Ids`：默认参与玩家组。
- `Host`：联赛主场组（先手）。

## 3. AI 总体决策流程

项目中较新的实现（如 `g08/g09`）通常遵循以下优先级：

1. **立即胜着检测**：若当前能直接形成六连，立即执行。
2. **致命威胁防守**：优先处理对手活四、冲四、复合威胁（双活三/双冲四/四三）。
3. **威胁空间搜索（TBS）**：尝试发现强制胜负链。
4. **Alpha-Beta 深度搜索**：在候选着法上做迭代加深博弈搜索。
5. **启发式回退**：若搜索失败或超时，返回排序靠前的启发式着法。

该顺序本质是“战术正确性优先于战略最优性”：先避免漏防和漏杀，再追求更深层最优。

## 4. 核心算法与原理

### 4.1 候选点生成与裁剪（Move Generation）

由于全盘空位过多，直接全展开不可行。实现中通常采用：

- 只在已有棋子附近生成候选点。
- 对候选点按威胁分/形状分/位置分排序。
- 限制每层最多展开前 $K$ 个候选双子着法。
- 中后盘按触发阈值适度扩边，减少“远处漏防”。

这相当于先用启发式函数近似真实价值函数，把搜索预算集中到高价值区域。

### 4.2 威胁识别（Threat Evaluation / Analysis）

通过扫描四个方向的局部棋型，识别：

- 活三、冲四、活四、连五/连六趋势
- 复合威胁（双活三、双冲四、四三）

原理上，威胁识别相当于构造局部模式匹配器，并对每种模式赋予战术优先级。其作用是：

- 指导防守点提取（必须堵哪些点）
- 指导候选排序（哪些进攻更迫使对手应手）
- 触发搜索延伸（threat extension）

### 4.3 Alpha-Beta 剪枝 + 迭代加深

在零和博弈中，使用极大极小搜索：

$$
V(s) = \max_{a \in A(s)}\left(-V(T(s,a))\right)
$$

Alpha-Beta 用上下界 $(\alpha,\beta)$ 提前剪掉不可能更优的分支；迭代加深从浅到深逐层搜索，随时可返回当前最好解（满足时间约束）。

项目中的常见工程优化：

- PVS（Principal Variation Search）空窗试探
- Killer Move / History Heuristic 着法排序
- 威胁延伸（在战术紧张节点额外加深）
- Quiescence（静态搜索）减少地平线效应

### 4.4 威胁空间搜索（TBS, Threat-Based Search）

TBS 关注“我方连续制造强威胁，对方被迫防守”的强制链。

- 攻击层（OR）：我方是否存在一种威胁着法能继续保持必胜希望。
- 防守层（AND）：对手所有关键防守是否都无法化解我方胜势。

若 OR/AND 递归成立，可得到近似“证明式”的强制胜路线。TBS 对中盘战术非常有效，能快速捕捉常规估值搜索不易发现的杀棋链。

### 4.5 置换表（Transposition Table, TT）与 Zobrist 哈希

同一局面可由不同落子顺序到达。TT 用哈希键缓存已搜索结论，避免重复计算。

- 使用 Zobrist 哈希对局面做增量异或更新。
- 缓存项可带边界类型：`EXACT / LOWER / UPPER`。
- 在 Alpha-Beta 与 TBS 中共享缓存，提升命中率与整体效率。

这本质上是在博弈树上做“动态规划式复用”。

## 5. 各组实现特点（简要）

- `g06`：V2 基线框架，强调威胁防守与 Alpha-Beta 搜索。
- `g08`：V3 组合策略，加入 TBS、PN 思想入口、TT 共享、更强防守规则与搜索优化。
- `g09`：沿用并强化“威胁优先 + TBS + Alpha-Beta”的流程，参数更偏实战平衡。

## 6. 参数调优建议

可优先调以下参数：

- 搜索深度与单步时间预算（速度 vs 质量）
- 每层最大候选数（分支宽度）
- 威胁评分权重（进攻倾向 vs 防守倾向）
- TBS 最大深度与候选上限
- TT 容量（内存占用 vs 命中率）

建议采用固定对手池做 A/B 测试，观察：

- 胜率
- 平局率
- 平均用时
- 平均搜索节点数与剪枝率

## 7. 常见问题

### 7.1 运行时报缺少依赖

请确认 `lib/` 已完整复制并正确加入 classpath。部分仓库镜像可能不包含该目录。

### 7.2 AI 出现“会进攻但漏防”

通常是威胁检测覆盖不足或候选裁剪过激。优先检查：

- 致命威胁提取逻辑
- 候选扩边触发条件
- TBS/Alpha-Beta 前的保险防守流程

## 8. 后续可扩展方向

- 更强的 Proof-Number Search（PN/DFPN）与 TBS 协同。
- 基于自对弈数据的参数学习（权重自动调优）。
- 开局库与残局库。
- 并行搜索与多核优化。
- 更稳定的时间管理策略（按局面复杂度分配预算）。
